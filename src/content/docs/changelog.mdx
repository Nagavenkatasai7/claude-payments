## 2026-10

- **Reason for "other".** When `purpose` is `other`, `POST /transactions` now requires `purpose_detail`: the sender's reason in their own words, 10 to 120 characters that say what the money is for. A missing, too short, too long or meaningless value is refused with `422` before the `Idempotency-Key` is bound, so a corrected retry with the same key succeeds. When the reason names one of the other purposes (for example "school fees"), the transaction takes that purpose and keeps the reason. With any other purpose, `purpose_detail` is ignored. It comes back as `purpose_detail` in every answer, to the partner that owns the transaction only (`null` when none was given). SmartRemit checks every reason, and some transactions are held for review (`compliance_status` `flagged`).
- **Required purpose.** `POST /transactions` now requires `purpose`: why the money is sent, one of `family_support`, `gift`, `education`, `medical`, `savings`, `bills`, `business` or `other`. A missing or unknown value is refused with `422` before the `Idempotency-Key` is bound, so a corrected retry with the same key succeeds. It comes back as `purpose` in every answer (`null` on a transaction made before this change) and is in the settlement instruction's `compliance` object. Sandbox transactions need it too.
- **New documentation preview.** These guides and an API reference generated from the Partner API's OpenAPI description.
- **Order references.** Send your own order number as `client_reference` when you create a transaction. It comes back in every answer and in the settlements statement, and it is in the settlement instruction when your own rail pays the transaction out. A `paid_out` status callback may send `payout_reference` (for example a bank UTR); it is saved once and returned as `payout_reference`.

## 2026-09

- **Test keys and scopes.** Keys are now live (`sr_live_…`) or test (`sr_test_…`), and each endpoint needs one scope. A test key works only with sandbox transactions, which never reach a real payout rail.
- **Per-key rate limit.** Each key now has its own per-minute budget, inside the per-partner one.
- **Settlements statement.** `GET /settlements` lists your paid and delivered transfers for reconciliation, as JSON or CSV.
- **Timestamped signatures.** Instructions and callbacks are signed with `x-smartremit-signature` (timestamp plus HMAC), with an overlap window when a secret is rotated. The older `x-signature` header is deprecated.
- **Compliance block.** Settlement instructions carry an additive `compliance` object.
- **Sender name.** A transaction created without `sender.name` is held for manual review.
- **Idempotency hardening.** The transaction is bound to its `Idempotency-Key` before it is created, reserved key prefixes are refused, and a masked payout account is refused.
- **Unpaid expiry.** A transaction left unpaid is cancelled after a fixed period.
- **Exchange rates fail safely.** A quote or transaction is refused with `503` rather than priced on a stale or missing rate.
- **Settlement endpoint rules.** Settlement endpoints must be public HTTPS hosts; redirects and acknowledgement sizes are limited.

## 2026-06

- **Partner API v1.** Key authentication, per-partner rate limit, and the corridors, quote, beneficiaries and transactions endpoints.
- **Webhook-driven settlement.** Signed settlement instructions to your rail and signed status callbacks back, with automatic retries.
- **Rates.** `PUT /rates` and `GET /rates` let you push a wholesale rate per corridor.
- **Any-to-any corridors.** `destination_country` on quotes and transactions.
